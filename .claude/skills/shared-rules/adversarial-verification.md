# 对抗验证协议（Adversarial Verification Protocol）

> **加载时机**：结论性产出验证时（code-reviewer 审查结论、planner RESEARCH/DESIGN-REVIEW、cc-api-analyzer aggregator）。派发独立 agent 做混合对抗验证（定向推翻 + 盲区扫描）。

---

## 一、适用范围

| 触发点 | Skill | 验证对象 | 验证 agent 输入 |
|--------|-------|---------|----------------|
| 审查结论 | code-reviewer（阶段9后） | 问题列表 + 置信度 | 原始代码 + 变更范围 + **初始问题列表**（不含推理链） |
| 研究发现 | planner RESEARCH 完成时 | findings.md | 原始需求 + 代码范围 + **初始 findings 结论**（不含推理链） |
| 设计评审 | planner DESIGN-REVIEW | 评审意见 | 设计文档 + 原始需求 + **初始评审意见**（不含推理链） |
| 接口分析 | cc-api-analyzer aggregator 阶段 | 表关系 + ER 推断 | 原始分析报告 + **初始 ER 推断**（不含推理链） |
| 通用方案产出 | Stop hook 自动触发（双条件） | 方案要点 | 原始需求/问题 + **方案结论**（不含推理链） |
| 分析/调研结论 | Stop hook 自动触发（双条件） | 分析结论 | 原始材料摘要 + **分析结论**（不含推理链） |
| 排查/诊断结论 | Stop hook 自动触发（双条件） | 根因判断 | 问题描述 + 已知线索 + **诊断结论**（不含推理链） |

> **通用场景触发机制**：由用户手动触发 `/cc-adversarial`，或由 Skill 工作流在结论性产出后内置调用。
>
> **Stop hook 双条件门槛**（2026-04-08 新增，来源: iMAD 57-85% 辩论不必要）：
>
> 同时满足以下两个条件才自动触发，单一条件不触发（避免"验证疲劳"）：
>
> 1. **数量条件**：结论数 ≥3 条（1-2 条结论不需要对抗验证，单条确认即可）
> 2. **不确定性条件**：结论中含任一信号 → 含对冲用语（"应该"、"大概率"、"可能"）、涉及 trade-off/方案选型、含跨模块/并发/事务场景
>
> **永远触发例外**：P0 关键词 + 核心改动（见 cc-adversarial/SKILL.md §P0 关键词）— 双条件不满足时仍强制触发。

### 跳过条件（低风险变更）

以下场景可跳过对抗验证，直接放行：

| 条件 | 说明 |
|------|------|
| 变更 LOC ≤ 30 且单文件 | 影响面极小 |
| 纯 DTO/枚举/配置类变更 | 无业务逻辑风险 |
| 用户明确说"跳过验证" | 人工覆盖 |
| 文档/注释唯一改动 | 无行为变更 |

**恢复条件**：即使满足跳过条件，涉及 P0 关键词（`@Transactional`、`synchronized`、`DELETE`、`DROP`、支付/金融）时恢复完整验证。

## 二、核心原则

1. **混合对抗** — 验证 agent 接收初始结论的**结果**（不含推理链），在定向对抗中融合覆盖补充：
   - **逐条对抗**：审视初始结论，尝试找反例推翻
   - **收尾覆盖补充**：检查未读文件和未覆盖区域，发现初始分析可能遗漏的问题
2. **推理隔离** — 验证 agent 只接收初始结论的结果清单，不接收推理过程。防止推理链"说服"验证方
3. **聚焦分歧** — 最终输出重点关注两方分歧点和盲区发现，共识点简要列出
4. **验证质量保障** — 验证 agent 必须满足最低产出要求（见 §4），否则验证视为无效，需重新派发

> **为何混合对抗**：纯对抗（只推翻）会遗漏初始分析完全没覆盖的盲区；纯独立分析（同模型）容易产生相同偏见。混合模式兼顾两者。

## 三、验证流程

```
初始分析完成
    |
    v
准备验证输入
    |  原始材料（代码/需求/文档）
    |  + 初始结论结果清单（结构化，不含推理链）
    |
    v
派发 conclusion-verifier agent
    |  逐条对抗初始结论 + 收尾覆盖补充
    |  max_turns: 按场景选择（见 §4）
    |
    v
验证质量检查
    |  覆盖维度 >= 最低要求？
    |  读取文件数 >= 最低要求？
    |  ├─ 不满足 → 标记验证无效，重新派发（最多 1 次）
    |  └─ 满足 → 继续
    |
    v
综合对比（见 §5）
    |
    ├─ 共识点 → 直接采用（high）
    ├─ 分歧点
    |   ├─ P0 分歧 → 强制升级用户确认（Lead 不自裁）
    |   ├─ P1+ 可判定 → Lead 裁决，说明理由
    |   └─ P1+ 不可判定 → 标记"待用户确认"
    ├─ 验证方关联发现（Phase A 副产物） → 补充，标记"对抗关联发现"
    └─ 验证方独立发现（收尾覆盖补充） → 补充，标记"盲区发现"
    |
    v
输出综合结论
```

## 四、验证 agent 规格

### 通用约束（嵌入验证 agent prompt）

> **与 prompts.md 的关系**：本节 prompt 用于被动内嵌场景（code-reviewer/cc-planner/cc-api-analyzer 直接调用）。用户主动 `/cc-adversarial` 时使用 `cc-adversarial/prompts.md` 的分角色 prompt（含评分量表、P0 升级标记、对立假设等增强功能）。

```
你是一个混合对抗验证 agent。你的工作流程：

**Phase A — 定向对抗 + 覆盖补充**：
你会收到初始结论的结果清单（不含推理过程）。逐条审视：
1. 对每个结论，问"这个结论在什么条件下会失败？"，然后去代码中验证
2. 找到反例 → 记录为"反驳"，附带代码证据
3. 找不到反例 → 记录为"确认"，说明你检查了什么
4. 对抗过程中发现相关但不在初始结论列表中的问题 → 记录为"关联发现"
5. **收尾步骤（必做）**：检查初始结论中是否有你完全没读取相关文件的条目
   → 有：快速读取并给出判定
   → 无：检查是否有初始结论未覆盖的文件在变更范围内
      → 有：快速扫描，记录为"盲区发现"
      → 无：输出"无额外发现"

**强制规则**：
1. 同一操作失败 2 次后换方法或标记失败并停止
2. 输出不超过 200 行，优先保留：反驳证据 > 盲区发现 > 确认共识
3. 校准与防偏规则详见 cc-adversarial/SKILL.md Gotchas（推理隔离、文件范围限定、株连效应校准、否定偏差校准）

**FLCA 四维度评分（每条结论必须输出 F/L/C/A 各 1-10 分）**：

| 维度 | 含义 | 评分参考 |
|------|------|---------|
| F 依据 | 结论的前提/事实是否成立 | 8-10 有充分证据 / 5-7 部分有据 / 1-3 找到反例 |
| L 逻辑 | 从前提到结论的推理是否完整 | 8-10 推理严密 / 5-7 有跳步 / 1-3 因果断裂 |
| C 覆盖 | 是否考虑必要的维度、边界、替代方案 | 8-10 全面 / 5-7 有遗漏 / 1-3 重大盲区 |
| A 可行 | 结论是否具体到可指导下一步行动 | 8-10 可直接落地 / 5-7 方向对但需细化 / 1-3 模糊 |

**判定规则（放宽版，对齐 cc-adversarial/prompts.md §共享约束）**：
- **❌ 有误**：任一维度 ≤3（极低分才否决，避免单维度低分连坐否决）
- **✅ 确认**：4 个维度均 ≥6 且无 ≤4（均值 ≥6 即可确认，中性方案也能通过）
- **⚠️ 不完整**：其余（含任一 4-5、分差 >5 等情况，表示方向对但需补充）

**输出格式（必须）**：
## Phase A: 定向对抗
| # | 初始结论 | F | L | C | A | 判定 | 问题/确认依据 | 建议行动 |
|---|---------|---|---|---|---|------|-------------|---------|
| 1 | [结论摘要] | [1-10] | [1-10] | [1-10] | [1-10] | ❌有误/⚠️不完整/✅确认 | [有误:错在哪+为什么 / 不完整:缺什么 / 确认:验证了什么] | [有误/不完整:修正或补充建议 / 确认:—] |

> 判定规则: 任一≤3→❌有误 | 均≥6且无≤4→✅确认 | 其余→⚠️不完整

## 收尾覆盖补充
- [盲区发现 + 严重度P0/P1/P2 + 建议行动]
- [关联发现 + 建议行动]
- 无额外发现（如确实没有）

## 覆盖报告
- 已判定结论: #1, #2, #5, #7（N/M = X%）
- 未判定结论: #3, #4, #6（因 turn 不足跳过，列出原因）
- 读取文件: [列出已读取的文件]
```

### 最低产出要求

| 指标 | 最低要求 | 不满足时处理 |
|------|---------|------------|
| Phase A 覆盖率 | 初始结论的 ≥70% 逐条有判定 | 验证无效，重派（+2 turns） |
| 收尾覆盖补充 | 必须有收尾段落（即使结论是"无额外发现"） | 验证无效，重派 |
| 文件读取量 | ≥2 个不同文件 | 验证无效，重派 |
| 覆盖报告 | 必须包含 | 验证无效，重派 |

> 重派最多 1 次。两次均不满足 → 标记"验证不充分（覆盖 N%）"，Lead 在综合结论中注明，所有初始结论降为 medium-low 置信度。

### 场景化配置

> **⛔ subagent_type 白名单**：所有场景统一使用 `general-purpose`，与 `cc-adversarial/prompts.md` 白名单一致。

| 场景 | max_turns | 验证重点 |
|------|-----------|---------|
| 代码审查验证 | 8 | 逐条对抗问题列表；收尾扫描未覆盖的维度/文件 |
| 其他场景（研究/设计/接口/方案/调研/诊断） | 6 | 对抗结论证据充分性；收尾扫描遗漏维度/文件 |

## 五、综合对比算法

### 对比维度

按场景选择匹配键：代码审查用 `文件:行号+维度`，接口分析用 `表名对`，其余用 `结论主题/要点`。对比内容：结论描述、证据充分性、置信度。

### 综合规则

| 情况 | 归桶 | 处理 |
|------|------|------|
| 双方一致确认 | ✅ 已确认 | 直接采用 |
| 验证方反驳（找到反例） | ❌ 有误 | 附: 错在哪+为什么+建议修正 |
| 验证方存疑（方向对但不完整） | ⚠️ 不完整 | 附: 缺什么+影响+建议补充 |
| 初始方发现 + 验证方未覆盖 | ⚠️ 不完整 | 标注"未经验证"，建议补充验证 |
| 验证方盲区发现 | 💡 盲区发现 | 附严重度+建议行动 |
| **P0 分歧** | ❌ 有误 | **强制升级用户**，Lead 不自裁 |

### 分歧裁决防偏规则

| 分歧严重度 | 裁决方式 | 理由 |
|-----------|---------|------|
| **P0 分歧**（安全/数据完整性） | **强制升级用户**，Lead 不得自裁 | P0 误判代价极高，Lead 有锚定偏差 |
| P1 分歧 | Lead 裁决，但必须引用代码证据，不得仅凭推理 | 要求证据降低主观偏差 |
| P2+ 分歧 | Lead 裁决，简要说明理由 | 低风险，效率优先 |

> **防偏核心**：Lead 是初始结论的产出者，对自身结论有天然锚定偏差。P0 分歧不允许 Lead 自裁，必须交由用户判断。

## 六、输出格式

> 完整报告模板见 `cc-adversarial/templates/report-format.md`。以下为被动协议的精简版，供内嵌调用方使用。

### 综合结论报告（精简版）

> 完整模板见 `cc-adversarial/templates/report-format.md`。此处为被动内嵌调用的精简版，采用相同的三桶模型。

```markdown
## 对抗验证结论

**{一句话总结 — 示例: "5条中1条有误、1条不完整、3条确认"}**

### ❌ 有误（{N}条）— 必须修正
| # | 原结论 | 错在哪 | 为什么错 | 建议修正 |
|---|--------|--------|---------|---------|

### ⚠️ 不完整（{N}条）— 建议补充
| # | 原结论 | 缺什么 | 影响 | 建议补充 |
|---|--------|--------|------|---------|

### ✅ 已确认（{N}条）
- [结论摘要 — 验证方式]

### 💡 盲区发现
- [发现 + 严重度 + 建议行动]

### 待用户确认（P0 分歧强制）
- [P0 分歧点，附双方论据和代码证据]

> 覆盖率: {已验证}/{总数} | 独立发现率: {X}%
```

## 七、可观测性日志

验证启动时输出：
```
🔍 对抗验证: [场景] | 输入: [原始材料摘要] | 初始结论: {N}条
```

验证完成时输出：
```
🔍 验证完成: 确认 {N} | 反驳 {N} | 盲区 {N} | 未覆盖 {N} | 独立发现率: {X}% | 质量: [充分/不充分]
```

## 八、与现有机制的关系

- **code-reviewer 阶段9**（自检）→ 对抗验证在自检之后，是更高层级的独立验证
- **planner multi-llm-review** → 已废弃，被本协议替代
- **code-writer 统一审查** → 对抗验证是审查阶段增强，不影响审查流程
