> **加载时机**：code-reviewer/code-writer 审查流程中按需加载。

## 一、复杂度分级与 Skill 推荐

| 级别 | 文件数 | 代码行数 | 任务数 | 模块跨度 | 推荐 Skill |
|------|--------|---------|--------|---------|-----------|
| 小型 | 1-2 | ≤ 50 LOC | 1-3 | 单模块 | code-writer（planner 内可主 agent 直接实现） |
| 中型 | 3-5 | 51-300 LOC | 4-7 | 2-3 模块 | planner → code-writer |
| 大型 | 6-10 | 301-800 LOC | 8-15 | 3+ 模块 | planner → work-mode |
| 超大型 | > 10 | > 800 LOC | > 15 | 跨系统 | design → planner → work-mode |
| 分析型 | N/A | N/A | >= 2 | N/A | planner 自身并行 ★ |

### 并发度选择

| 任务数 | 并发度 | 使用 Skill |
|--------|--------|-----------|
| < 5 | 顺序执行 | code-writer |
| >= 5 且任务已明确 | 10 并发 | work-mode |
| > 10 | 10 并发 + 分批 | work-mode |
| >= 2（分析型） | 10 并发 | planner 自身 ★ |

## 二、审查触发与跳过

### 审查触发阈值

| 指标 | 阈值 | 触发审查类型 |
|------|------|-------------|
| 变更行数 | > 100 LOC | 基础审查 |
| 变更行数 | > 300 LOC | 深度审查 |
| 新增文件数 | > 3 | 架构审查 |
| 涉及事务代码 | 是 | 事务专项审查 |

### 审查跳过条件

| 条件 | 可跳过的审查阶段 |
|------|-----------------|
| < 50 LOC 单文件且不涉及 P0 关键词 | **快速通道**：仅执行 Stage1，跳过 Stage2，跳过对抗验证 |
| < 30 LOC 且不涉及任何安全/事务/支付关键词 | 跳过 Stage2 + 跳过对抗验证（仅执行 Stage1） |
| 仅新增 DTO/枚举类 | 跳过 Stage1（仅执行 Stage2 代码质量），跳过对抗验证 |

> **快速通道与对抗验证的关系**：上述三种跳过条件同时跳过 `adversarial-verification.md` 定义的对抗验证流程。理由：低风险变更的对抗验证 ROI 过低。但若任何跳过条件中涉及 P0 关键词，则恢复完整流程（含对抗验证）。

> **P0 关键词**：`@Transactional`、`synchronized`、`FOR UPDATE`、`DistributedLock`、`ThreadPoolTaskExecutor`、支付/退款/金额计算、`DELETE`/`DROP`/`TRUNCATE`

## 三、审查流程

> 数据格式的唯一定义见 `data-contracts.md`。

### 审查请求格式（→ code-reviewer）

| 调用来源 | 审查模式 | 可跳过 |
|---------|---------|--------|
| cc-code-writer | 统一审查 | ❌ |
| cc-work-mode | 阻断式强制 | ❌ |
| 用户直接请求 | 建议式 | ✅ |

**统一审查门控流程**：

> 注: code-writer 已将两阶段合并为统一审查模式，以下流程仅供 reviewer 独立使用时参考。

```
Stage 1: 规范合规检查（P0-P1）
├─ 安全审查（P0）
├─ 数据完整性（P0）
├─ 业务行为验证（P0）— 状态机/流程顺序错误归入 P0
├─ 流程顺序验证（P0）— 与业务行为同级，执行前必须通过
└─ 架构合规（P1）
    ↓
├─ 通过 → 进入 Stage 2
└─ 不通过 → 返回修复（详见下文"异常处理"）

Stage 2: 代码质量检查（P2-P5）
├─ 单元测试（P2）
├─ 性能优化（P3）
├─ 设计模式（P4）
└─ 代码简化（P5）
    ↓
├─ 通过 → 审查完成
└─ 有问题 → 建议优化（非阻断，记录到技术债务）
```

## 三-B、验证闭环铁律

> 来源：obra/superpowers verification-before-completion + 全局 CLAUDE.md §3

**铁律：无验证证据，不可宣称完成。**

宣称"已完成"、"已修复"、"已通过"前，必须：
1. **识别**：什么命令/操作能证明这个声明？
2. **执行**：运行该命令（必须是当前消息内的新鲜执行，不可引用历史结果）
3. **确认**：输出符合声明 → 附证据宣称；不符合 → 陈述实际状态

| 产出类型 | 验证方式 | 示例 |
|---------|---------|------|
| 代码变更 | 运行测试 + 确认退出码 | `mvn test` exit 0 |
| 配置修改 | diff 检查 + 相关服务验证 | `git diff` 确认变更范围 |
| 文档/设计 | 人工确认（明确标注"待人工确认"） | "设计文档已生成，待评审" |
| 脚本执行 | 执行 + 检查退出码和输出 | 脚本输出 + exit 0 |
| Bug 修复 | 重现原始症状的测试必须通过 | 回归测试 green |

**红灯词**（出现即违反）：~~应该通过~~、~~大概率没问题~~、~~看起来正确~~

## 四、异常处理协议

> 每个协作节点的失败处理必须明确定义，禁止"报告用户"后无后续。

### 超时分层说明

- **Skill 间调用超时**（本章定义）：控制 Skill A 调用 Skill B 的等待时间
- **Skill 内部超时**（各 SKILL.md 定义）：如 cc-work-mode 的 executor 15min/批次 20min/整体 60min

> **注意**: 超时值为指导性建议，Claude Code 不提供原生超时强制机制。实际超时由 max_turns 间接控制。

### 调用类型的异常处理

| 调用类型 | 超时 | 重试上限 | 回退策略 |
|---------|------|---------|---------|
| 顺序调用 | 10 min | 2 次 | 跳过当前步骤 → 检查后续依赖 → 满足则继续 → 不满足则终止并报告 |
| 自动委托 | 10 min | 2 次 | 回退到委托前状态 |
| 自动委托+门控 | 无超时 | 门控内 3 次修改 | 第 4 次提供选项：继续/跳过/重规划 |
| 统一审查 | 5 min | 3 次 | 3 次后报告用户，附失败原因和建议 |
| 阻断式强制 | 10 min | 2 次 | 必须通过，不可跳过；2 次后人工介入 |

### 审查失败完整处理链

```
code-writer → code-reviewer（统一审查）
  ├─ P0-P1 问题 → 阻断，返回 code-writer 修复
  │   ├─ 第 1-2 次：自动修复 → 重新提交审查
  │   └─ 第 3 次：停止，报告用户，附：失败问题列表 + 建议修改方案
  └─ P2+ 问题 → 建议优化（记录到 .claude/tech-debt.md，不阻断）

work-mode → code-reviewer
  ├─ 通过 → 完成
  └─ P0/P1 问题 → 必须修复（返回 executor 修复，重试 2 次）
      └─ 仍失败 → 人工介入，附具体问题和影响分析
```

### 设计评审重试上限

| 评审轮次 | 处理 |
|---------|------|
| 第 1-3 次"需要修改" | 记录修改意见，重新委托 design 生成 |
| 第 4 次 | 强制暂停，提供选项：(A)继续修改 (B)跳过设计直接实现 (C)重新规划 |

### 并发状态隔离

work-mode 的 10 并发 executor：
- 每个 executor 写独立的进度文件：`progress.task_{id}.md`
- SUMMARIZE 阶段统一合并到 `progress.md`
- executor 间禁止读写同一文件（冲突时由 orchestrator 排队）

### Git 回退策略

```
增量提交策略：
  每组完成后：git tag savepoint-group-{N}
  组失败时：git reset --soft savepoint-group-{N-1}（只回退失败组）
  禁止：git reset --soft HEAD~1（会回退上一组的工作）
```
