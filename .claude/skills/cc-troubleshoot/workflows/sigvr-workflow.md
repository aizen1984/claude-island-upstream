# SIGVR 五阶段排障工作流

## S -- 症状确认（Symptom）

**目标**：明确问题是什么、影响谁、什么时候发生。

**步骤**：

1. **解析用户输入**，提取关键参数：

| 参数 | 示例 | 默认值 |
|------|------|--------|
| 问题描述 | "用户退款失败" | 必填 |
| 环境 | prod/sit | prod |
| 应用名 | vipship | 从问题推断 |
| 用户ID/订单ID | uid=123 | 无 |
| traceId | abc123def | 无 |
| 时间范围 | 今天上午10点 | 最近1小时 |

2. **Vault 域知识检索**（强制）：按全局 CLAUDE.md 的 L0->L1->L2 协议检索项目 Vault，获取业务上下文。打印检索日志。

3. **形成初始假设**（1-3 个，按可能性排序）：
```
**初始假设**：
- H1: [最可能] {假设描述}
- H2: [次可能] {假设描述}
- H3: [低可能] {假设描述}
```

4. **复杂度判定**（强制，决定后续流程和报告模板）：

基于问题描述和初始假设，明确声明复杂度级别：

| 级别 | 判断依据 | 流程 | 报告模板 |
|------|---------|------|---------|
| **L0 轻量** | 单点问题，假设指向同一组件；预计 ≤3 条查询；用户描述明确具体 | S → I → R（跳过 G/V） | `report-template-lite.md` |
| **L1 标准** | 多源涉及需交叉验证；4-8 条查询；多个维度 | 完整 SIGVR | `report-template.md` |
| **L2 复杂** | 跨服务/性能抖动/偶发 NPE；>8 条查询；多根因 | SIGVR + 扩展章节 | `report-template.md` |

**输出格式**（必须在对话流显示）：
```
复杂度判定: L{0/1/2}
理由: {一句话说明为什么}
预计证据: {SLS:N / SQL:N / CODE:N}
```

**示例判定**：
- ❌ `"服务 504 超时"` → L1（症状模糊，需多源定位）
- ✅ `"user 123 退款失败 RB623016 户名错误"` → L0（指向明确，查退款单+用户中心即可）
- ✅ `"商品列表偶发空白"` → L2（偶发+前后端交叉，需要性能 + 日志 + 代码）

5. **缺少关键参数时**，向用户提问（最多问 2 轮，不要反复追问）。

**门控**：至少有问题描述 + 时间范围 + **复杂度判定** 才能进入 I 阶段。

---

## I -- 信息收集（Investigate）

**目标**：多源取证，发散搜集证据。

**调查顺序**（按假设优先级动态调整，典型顺序）：

### 1. SLS 日志查询

通过 cc-sls-query 的 MCP 工具直接调用：

- 先查 ERROR 日志定位问题范围
- 发现 traceId 后做跨应用追踪（**不加 context 过滤**）
- 每次查询记录为 `[SLS-N]` evidence item

**关键 MCP 工具**：
- `mcp__sh_aliyun_observability__sls_execute_sql_query` -- 执行 SLS 查询
- `mcp__sh_aliyun_observability__sls_translate_text_to_sql_query` -- 自然语言转 SLS SQL
- `mcp__sh_aliyun_observability__sls_describe_logstore` -- 查看字段结构

**SLS 查询参数映射**：详见 `cc-sls-query/SKILL.md` 中的权威映射表（覆盖 3 集群 × 4 环境 × 2 类型）。本文件不再维护二手表，避免 DRY 失配——历史上简化为 prod/sit + 数禾/重庆小贷的二手表已过期，全量映射只在 cc-sls-query 一处维护。

### 2. 数据库查询

通过 sql skill 脚本调用：

```bash
# 查表结构（先看索引）
python3 .claude/skills/cc-sql/describe.py "表名" --indexes-only

# 查数据
python3 .claude/skills/cc-sql/query.py "SELECT 字段 FROM 表 WHERE 条件 LIMIT N"
```

- **强制**：WHERE 条件必须对齐索引列
- **强制**：每条 SQL 的 WHERE 参数标注来源 `<- evidence ID`
- **强制**：SELECT 字段必须包含业务详情列（info/detail/remark/ext_info/reason 等），不能只查 ID 和状态字段。先用 `describe.py` 查看全量字段，识别哪些列可能包含排障所需的业务上下文
- 每次查询记录为 `[SQL-N]` evidence item

### 3. 配置查询（按需）

通过 cfg skill 脚本调用：

```bash
python3 .claude/skills/cc-cfg/query.py "配置key" [-a 应用名]
```

- 当日志或代码中发现 `@ConfElement` 或配置驱动的分支逻辑时触发
- 记录为 `[CFG-N]` evidence item

### 4. 源码分析

通过 Read/Grep/Glob 直接操作：

- 从日志中的 logger 类名定位源码文件
- 追踪异常抛出点、条件分支、状态机转换
- **每个发现必须引用 `file:line`**
- 记录为 `[CODE-N]` evidence item

### 逐层推导规则（强制，不可跳级）

调查必须逐层展开，**禁止跳级推导**。每一层的输出是下一层的输入，中间不能有断裂：

```
X 错误：SLS-1 发现 uid=123 -> 直接结论"退款渠道拒绝"（跳过了数据库验证和代码确认）
O 正确：SLS-1 发现 uid=123 -> SQL-1 查订单状态 -> CODE-1 确认状态含义 -> SLS-2 追踪渠道响应 -> 结论
```

- **每个中间值都要查证**：日志里看到 status=3，不能直接说"失败"，必须通过 CODE-N 确认枚举含义
- **每次跨数据源都要衔接**：从日志到数据库、从数据库到代码、从代码到配置，每次跨越都要写明"我用了什么值（来自哪里）去查了什么"
- **数据流向必须显式**：不能出现"根据分析"这类模糊表述，必须写明具体是根据哪条 evidence 的哪个字段
- **正向证明，不可反推叙述**：即使排障过程是反向推理（从结果反推原因），报告中必须正向讲述完整链路。读者看完报告后，应能从起因到结果顺序理解整个问题，而不是看到一堆散乱的反推碎片

### 正向叙述原则（强制）

排障过程中可能是反推的（先看到错误，再找原因），但**报告必须正向讲述**：

```
X 反推叙述：我们发现退款失败 -> 查日志发现渠道拒绝 -> 反查发现是余额不足
O 正向叙述：用户发起退款请求 -> 系统调用支付宝渠道 -> 渠道返回"余额不足" -> 系统标记退款失败（status=3）-> 用户看到退款失败
```

报告的「根因分析 -> 因果链」部分，必须按**业务时间线正序**描述：
1. 触发动作是什么（用户做了什么 / 定时任务触发了什么）
2. 系统处理经过了哪些步骤（按代码执行顺序）
3. 在哪个步骤出了问题（代码定位 file:line）
4. 问题如何传导到用户可见的症状

### 收敛规则

- 每收集 3-5 条证据后评估：能否缩小到单一根因？
- 最多 10 轮查询（安全阀），超过强制进入 G 阶段
- 每条 evidence item 的结论必须关联假设（证实/否定/引出新假设）

### 复杂度动态调整（强制检查）

I 阶段每收集 3 条证据后，重新评估复杂度并可能升/降级：

| 触发条件 | 当前级别 | 调整到 | 动作 |
|---------|---------|--------|------|
| 前 3 条证据已形成闭环（互相印证、根因明确） | L1 | **L0** | 跳过 G/V，直接进 R 阶段，用 lite 模板 |
| 出现单源无法验证的关键结论 | L0 | **L1** | 补跑 G/V 阶段，改用完整模板 |
| 发现跨多服务/性能抖动/根因可能多个 | L1 | **L2** | 继续 SIGVR，报告用完整模板加扩展章节 |

**降级输出**（L1 → L0 时必须声明）：
```
✅ 证据闭环检测：前 3 条证据已互相印证，根因明确
复杂度降级: L1 → L0
跳过阶段: G, V
下一步: R 阶段（lite 模板）
```

## G -- 整理分析（Gather）

> **⚠️ L0 跳过**：若 I 阶段已降级为 L0（证据闭环），跳过本阶段直接进 R。
> **L1/L2 必须执行**。

**目标**：将散乱证据组织为完整因果链。

**步骤**：

1. 加载 `references/evidence-chain-format.md`

2. 为每条 evidence item 补全格式（输入来源、预期vs实际、结论）

3. 构建证据依赖链箭头图：
```
SLS-1（起点）
  |---> SQL-1 <- 参数 from SLS-1
  |       \---> CODE-1 <- 值 from SQL-1
  \---> SLS-2 <- traceId from SLS-1
```

4. **逐层完整性检查**（强制）：从第一条证据到最终结论，逐跳检查：
   - 每条 evidence 的输入参数是否都能追溯到前一条 evidence 或用户输入？
   - 是否存在"跳级"——中间缺少数据库确认、代码验证、或配置查证？
   - 每个中间结论（如 status=3 意味着什么）是否有对应的 CODE-N 确认？

5. 确定根因链：哪些 evidence items 按什么顺序证明了根因

6. **检查证据链是否完整**——从症状到根因之间有无断裂？有空隙则回退到 I 阶段做针对性补查

---

## V -- 验证确认（Verify）

> **⚠️ L0 跳过**：若 I 阶段已降级为 L0（证据闭环），跳过本阶段直接进 R。
> **L1/L2 必须执行**。

**目标**：交叉验证，确保结论可靠。

**验证规则**：

| 规则 | 说明 |
|------|------|
| 双源验证 | 每条关键结论至少 2 个独立证据源支撑 |
| 单源标记 | 仅 1 个来源的结论标记 ? ，尝试补充验证 |
| 反证检查 | 是否存在与结论矛盾的证据？ |
| 全覆盖测试 | 根因解释能否覆盖所有已观察到的症状？ |

**输出**：交叉验证表

| 结论 | 证据来源 | 验证状态 |
|------|---------|---------|
| {结论} | {evidence IDs} | V / ? |

---

## R -- 报告输出（Report）

**目标**：生成结构化诊断报告。

**步骤**：

1. **根据复杂度选择模板**：

| 复杂度 | 加载模板 | 目标长度 |
|--------|---------|---------|
| **L0** | `references/report-template-lite.md` | ≤60 行（单屏可读） |
| **L1** | `references/report-template.md` | 100-200 行 |
| **L2** | `references/report-template.md` + 扩展章节 | 200-400 行 |

2. **报告输出前必须画分隔符**：在对话流中先输出一条 `---` 分隔符，明确告知"以上是排障过程，以下是最终报告"。读者即使只读分隔符之下也能完整理解问题。

3. **过程信息过滤**（强制，报告不得包含以下内容）：
   - ❌ H1/H2/H3 初始假设清单
   - ❌ 🔗 委托日志（`🔗 cc-troubleshoot.INVESTIGATE → cc-sql ...`）
   - ❌ 失败的 SQL 重查过程（如 order_id 没命中改用 uid 的过程）
   - ❌ 废弃的中间假设
   - ❌ describe.py 全量字段输出
   - ❌ ★ Insight 教学块（除非用户明确要求）

4. 按模板填充所有必填章节（空章节可删除）

4.5. **Quote Grounding 自审（data-report-protocol §二，强制）**：

   报告生成后、质量检查清单前，对每条 CODE-N 证据 + 根因结论执行 [REMOVED:no-quote] 自审：

   - **每条 CODE-N 证据**：除保留原 `(CODE-N)` 引用外，必须附 `<quote file="文件路径" line="行号">原文字符逐字</quote>`。原文是 Read 工具读到的真实字符，禁止改写/总结
   - **根因结论行**：必须以 `<quote file="..." line="...">关键代码片段</quote>` 起头
   - **找不到原文支持的结论**：从报告中删除并在末尾"诊断备注"章节标注 `[REMOVED:no-quote] 原结论 #X: <摘要>，因无 quote 支持删除`
   - **scan_complete 声明**：如果排障过程因日志缺失/权限不足/SLS 索引不完整导致**未覆盖某些时间段或维度**，必须在报告"调查范围"章节末尾输出 `scan_complete: false | 未覆盖: [具体说明]`，禁止假装查全
   - **SLS/SQL/CFG 类证据例外**：保留原 evidence ID 即可（无对应文件可 quote）

5. 执行对应模板的「质量检查清单」

6. 输出到终端（默认）

**持久化**（可选）：用户说"保存到vault"或使用 `--save` 参数时：
- 写入 `vault/{项目名}/运维/排障/{YYYY-MM-DD}-{问题摘要}.md`
- 检查目录是否存在，不存在则创建
- 写入后检查 `首页.md` 的 `search_index` 是否需更新
