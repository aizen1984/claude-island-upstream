# 排障诊断报告模板（轻量版 / L0）

> cc-troubleshoot skill 的 **L0 轻量** 报告模板。R 阶段当复杂度 = L0 时加载。
>
> **适用场景**：单点问题，初步假设指向同一组件，≤3 条查询即可闭环定位。
> **不适用场景**：多服务交叉、性能抖动、偶发问题、单源无法验证 → 使用完整版 `report-template.md`。
>
> **设计原则**：
> 1. **单屏可读**：目标 ≤60 行，不翻页看完
> 2. **四要素齐全**：现象 + 原因 + 代码（file:line）+ 数据（表.字段/SQL）必须都在
> 3. **过程归过程，结论归结论**：假设/废弃分支/🔗 委托日志不进报告，只在对话流

---

## 使用说明

R 阶段选择此模板时：

1. **检查前置条件**（任一不满足 → 改用 `report-template.md`）：
   - [ ] 证据链已形成闭环（所有关键结论至少有一个证据源）
   - [ ] 不存在未验证的单源关键结论
   - [ ] 根因指向单一组件（不是跨服务问题）
2. 按下面的模板填充，空章节可删除（不必保留占位）
3. 输出前执行「质量检查清单」

## 填充示例（真实案例）

> 基于 2026-04-07 月付会员退款 RB623016 户名错误案例。

```markdown
# 排障诊断：代付退款的系统姓名与银行卡开户名不匹配

> **耗时**: 约 15 分钟 | 证据：SQL × 3 · CODE × 2

## 核心四要素

| 维度 | 内容 |
|------|------|
| **现象** | 月付会员退款 6 次全部失败，错误码 RB623016 "户名错误" |
| **影响** | 1 个用户（uid=39344d5c-06d1-474b-a3ca-4f3fa47dd440），卡号后 4 位 7917，¥179 |
| **根因** | 代付请求的收款人 name 写死取自用户中心 ("包金梅")，与银行卡实际开户名不符 |
| **代码** | `VipPaymentService.java:171` — `name(userInfo.getName())` 构建 MerchPayReq 时取用户中心姓名 |
| **数据** | `vip_account_info.name` = `"包金梅"`，`vip_refund_apply_info.refund_result` = 6 × `FAILED` |

## 证据

- **[SQL-1] 退款单状态确认** ← uid from 用户输入
  `SELECT refund_id, uid, refund_type, refund_result, refund_launch_time FROM vip_refund_apply_info WHERE uid = '39344d5c-06d1-474b-a3ca-4f3fa47dd440' ORDER BY refund_launch_time DESC`
  → 6 条记录，全部 `refund_result=FAILED`，`refund_type=BANK_CARD_PAY`（代付退款）

- **[SQL-2] 用户中心姓名确认** ← SQL-1.uid
  `SELECT uid, vip_no, name, mobile, status FROM vip_account_info WHERE uid = '39344d5c-06d1-474b-a3ca-4f3fa47dd440'`
  → `name = "包金梅"`，`status = OPEN`

- **[SQL-3] 交易日志错误确认** ← SQL-1.refund_id
  `SELECT refund_id, refund_status, message, created_at FROM vip_refund_trans_log WHERE uid = '39344d5c-06d1-474b-a3ca-4f3fa47dd440'`
  → 6 条 `message = "代付失败:RB623016:户名错误"`

- **[CODE-1] `VipPaymentService.java:167-178`**
  ```java
  MerchPayReq req = MerchPayReq.builder()
      .cardNo(vipPayInfo.getCardNo())       // 卡号来自 refund_info JSON
      .name(userInfo.getName())             // 姓名来自用户中心（写死）
      .build();
  ```
  → 代付请求的 name 字段固定取自用户中心姓名，不取银行卡开户名，导致系统姓名与卡实际开户名不符时必然失败

- **[CODE-2] `VipRefundWithMoneyService.java:87`**
  `VipPayInfo vipPayInfo = JSON.parseObject(vipRefundApplyInfo.getRefundInfo(), VipPayInfo.class)`
  → 退款卡号来源：从 `vip_refund_apply_info.refund_info` JSON 反序列化，与 userInfo 分离

## 因果链（正向）

```
客服发起退款 → 系统读 refund_info 取卡号 7917 + 读用户中心取姓名 "包金梅"
  → 组装 MerchPayReq 调用支付中台代付
  → 银行校验卡的实际开户名与请求中的 "包金梅" 不匹配
  → 返回 RB623016 "户名错误"
  → VipPaymentService 捕获异常写 vip_refund_trans_log.message = FAILED
  → 退款单 refund_result = FAILED
  → 客服看到"退款失败"提示
```

## 行动

- [ ] **客服**：联系客户确认卡号后 4 位 7917 的银行卡**实际开户名**是否为"包金梅"（注意生僻字/曾用名/他人代持）
- [ ] **客服（分支 A）**：若开户名非"包金梅" → 请客户提供本人名下银行卡，由客服重新录入卡号后发起退款
- [ ] **支付中台（分支 B）**：若开户名确为"包金梅"但仍报错 → 确认代付请求中实际传递的姓名字符串编码（Unicode 一致性/繁简体）

## 认知纠偏

> 客户反馈"已联系银行修改户名"——这是**误解**。银行侧修改的是银行自己的预留信息，但代付请求中的姓名是**我方系统（用户中心）**传给银行的，不是银行传给我方的。如果系统记录的姓名本身与卡的真实开户名不同，银行侧改什么都没用。解决路径只能是：要么换本人名下的卡，要么修正用户中心的姓名记录。
```

## 质量检查清单（L0 专用）

输出前逐项检查：

| # | 检查项 | 不通过则 |
|---|--------|---------|
| 1 | 标题是断言句（不是"根因分析"） | 改成 `# 排障诊断：{具体结论}` |
| 2 | 核心四要素表五行齐全（现象/影响/根因/代码/数据） | 补全缺失行 |
| 3 | 每条 SQL 完整可执行（无 `...` 省略，WHERE 有来源标注） | 补全 SQL |
| 4 | 每个 CODE 条目带 `file:line` | 补全行号 |
| 5 | 因果链是**正向**时间线（不是反推叙述） | 重写为正向 |
| 6 | 无 H1/H2/H3 初始假设、无 🔗 委托日志、无失败的重查过程 | 删除过程信息 |
| 7 | 行动条目可执行（有责任方，不是空泛建议） | 具体到人 + 动作 |
| 8 | 总行数 ≤60（不含认知纠偏） | 进一步精简或考虑用完整版模板 |

## 输出位置

- **默认**：终端直接输出
- **持久化**：用户说"保存到vault"时，写入 `vault/{项目名}/运维/排障/{YYYY-MM-DD}-{问题摘要}.md`
- 持久化前检查目标目录是否存在，不存在则创建
