# 排障诊断报告模板（完整版 / L1-L2）

> cc-troubleshoot skill 的 **L1/L2 完整版** 报告模板。R 阶段当复杂度 ≥ L1 时加载。
>
> **适用场景**：多源交叉验证、跨服务问题、性能抖动、需要交叉验证的复杂排障。
> **不适用场景**：单点问题，≤3 条查询即可闭环 → 使用 `report-template-lite.md`。
>
> **设计原则**：
> 1. 结论先行（BLUF），标题用断言句式
> 2. §1 TL;DR 即可行动，§2-§5 按需深入（Progressive Disclosure）
> 3. **过程归过程，结论归结论**：H1/H2/H3 假设/🔗 委托日志/失败重查**不进报告**，只在对话流
> 4. **去重**：因果链、证据依赖链、交叉验证三者曾经并列，现已合并——依赖链树中每个节点直接带验证状态标记，不再单独列交叉验证表
>
> **正反例**：❌ `## 3. 根因分析` → ✅ `## 3. 根因: 慢 SQL 占用连接导致连接池耗尽`

---

## 使用说明

1. 按模板填充，空章节可删除（不必保留占位）
2. §1 TL;DR 的"核心四要素"必填
3. §4 证据链逐条展开，每条标注输入来源
4. 输出前执行「报告质量检查清单」

---

## 模板

```markdown
# 排障诊断：{断言式标题，一句话根因}

> **生成时间**: {YYYY-MM-DD HH:mm}
> **排障耗时**: 约 {N} 分钟 | SLS × {N} · SQL × {N} · CFG × {N} · CODE × {N}

---

## 1. TL;DR（核心四要素）

| 维度 | 内容 |
|------|------|
| **现象** | {一句话描述现象} |
| **影响** | {受影响的用户/订单/服务数量 + 时间窗口} |
| **环境** | {prod/sit} · {应用名} · {集群} |
| **根因** | {为什么会这样，一句话可执行理解} |
| **代码** | `{file}:{line}` — {该行代码的作用} |
| **数据** | `{表名}.{字段}` = `{关键值}` / 关键 SQL：`{简化 SQL}` |

**关键发现**（⚠️ = 关键 · ✅ = 已验证双源 · ❓ = 单源待验证）：

- ⚠️ ✅ **{发现 1}**: {描述} （{evidence IDs}）
- ⚠️ ❓ **{发现 2}**: {描述} （{evidence IDs}）

---

## 2. 因果链（正向时间线）

> 从触发动作到用户可见症状，按业务时间线正序描述。即使排障是反推的，报告必须正向。

```
{1. 触发动作}
  → {2. 系统处理步骤 A}  @ {file:line}
  → {3. 系统处理步骤 B}  @ {file:line}
  → {4. 问题发生点 ⚠️}   @ {file:line}  ← 根因在此
  → {5. 传导路径}
  → {6. 用户可见症状}
```

## 4. 证据链

> 完整调查过程，每条查询可追溯输入来源。格式详见 `evidence-chain-format.md`。
> **注意**：此处只列**最终保留的证据**。过程中被否定的假设、失败的查询、重试过程**不要**进入本章节。

### [SLS-1] {断言式标题}

- **输入**: {参数} ← {来源}
- **查询**: `{完整查询语句}`
- **结果**: {关键字段和值}
- **结论**: {证实/否定 H?，引出下一步}

### [SQL-1] {断言式标题}

- **输入**: {uid = xxx ← SLS-1.uid}
- **查询**: `SELECT {字段列表} FROM {表} WHERE {条件} ← {来源标注}`
- **结果**: {返回的关键字段及值}
- **结论**: {…}

### [CODE-1] `{file}:{line}`

```{language}
{关键代码片段}
```

**作用**：{这段代码在问题中的角色}
**输入**：{何处触发这段代码}

### [CFG-1] {配置项}（如适用）

- **查询**: `cfg query '{key}' -a {应用}`
- **值**: `{配置值}`
- **作用**: {该配置如何影响行为}

---

### 证据依赖链（含验证状态）

> 树形依赖图，每个节点直接标注验证状态。**替代**原来分离的"依赖链 + 交叉验证表"两份结构。

```
SLS-1（起点：ERROR 日志）[✅ 唯一日志源]
  ├─→ SQL-1（订单状态：status=3）[✅ 2源 + CODE-1]  ← uid, orderId from SLS-1
  │     └─→ CODE-1（枚举确认：3=REJECTED）[✅ 代码直接引用]
  └─→ SLS-2（traceId 跨应用）[✅ 2源 + CODE-2]  ← traceId from SLS-1
        └─→ CODE-2（处理逻辑：不重试）[❓ 单源]  ← responseCode from SLS-2
```

**状态标记**：
- `[✅ N源]` — 至少 N 个独立证据源支撑该结论
- `[❓ 单源]` — 仅 1 个来源，未能交叉验证
- `[❌ 反证]` — 与其他证据矛盾，已否定

## 报告质量检查清单

输出报告前，逐项检查：

| # | 检查项 | 不通过则 |
|---|--------|---------|
| 1 | 标题是断言句（不是"根因分析"） | 改成 `# 排障诊断：{具体结论}` |
| 2 | §1 TL;DR 的"核心四要素"全部填充（现象/影响/根因/代码/数据） | 补全缺失 |
| 3 | 每条关键发现有验证状态标记（✅/❓/❌） | 补全状态 |
| 4 | §2 因果链是**正向**时间线（不是反推叙述） | 重写为正向 |
| 5 | §3 根因分析包含 `file:line` 代码定位 | 补全位置 |
| 6 | §4 每条 SQL 的 WHERE 参数有来源标注（`← evidence ID`） | 补全标注 |
| 7 | §4 证据依赖链的每个节点都标注了验证状态 | 补全 `[✅/❓]` |
| 8 | 无单源 ✅（单源只能标 ❓） | 修正状态 |
| 9 | §5 建议措施可执行（有责任方，有具体动作） | 具体化到人 + 动作 |
| 10 | **无过程污染**：不含 H1/H2/H3 假设、🔗 委托日志、失败重查过程 | 移出到对话流 |
| 11 | **无重复结构**：因果链、证据依赖链、代码定位不应三份并列 | 合并为依赖链一份 |

---

## 输出位置

- **默认**: 终端直接输出（报告即为回复内容）
- **持久化**: 用户说"保存到vault"时，写入 `vault/{项目名}/运维/排障/{YYYY-MM-DD}-{问题摘要}.md`
- 持久化前检查目标目录是否存在，不存在则创建
