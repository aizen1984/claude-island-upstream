# 上下文质量管理（Context Quality Management）

> **核心理论**：质量下降曲线 —— Claude 的输出质量随上下文使用率增加而下降

## 质量下降曲线

```
0-30% context:  峰值质量（全面、彻底、高质量输出）
30-50% context: 良好质量（投入、可控、正常执行）
50-70% context: 质量下降（压缩、效率模式、开始丢细节）
70%+ context:   质量崩溃（仓促、自我阉割、遗漏关键信息）

⚠️ 关键洞察：Claude 不是在 80% 才下降，而是在 40-50%
看到上下文堆积时就进入"完成模式"。到 80% 时质量已经崩溃。
```

## 三级上下文警告

| 剩余上下文 | 警告级别 | 强制动作 |
|-----------|---------|---------|
| **25%** | 🟡 黄色警告 | 立即保存检查点到 `{workspace}/progress.md` |
| **15%** | 🟠 橙色警告 | 完成当前任务后**停止**，输出恢复摘要 |
| **10%** | 🔴 红色警告 | **立即停止**，只写检查点，不执行新任务 |

## 上下文健康检查

每完成 3 个任务后（与 `{workspace}/progress.md` 追加同步），执行健康自检：

```yaml
context_health_check:
  # 重要决策 = 架构变更、方案回退、跨阶段跳转
  trigger: "每完成 3 个任务后 | 重要决策前"

  # 注意力刷新已内置于执行循环（每个任务前 Read {workspace}/spec.md + {workspace}/plan.md），此处仅做健康自检
  questions:
    - "我是否开始压缩输出？" → 是 → 保存检查点，考虑新会话
    - "回复是否开始变短？" → 是 → 上下文可能紧张

  actions:
    yellow_warning: "保存检查点，继续执行"
    orange_warning: "完成当前任务，停止，输出恢复摘要"
    red_warning: "立即停止，只写检查点文件"
```

## 50% 原则

**核心规则**：在 50% 上下文内完成所有核心工作。

- **RESEARCH + INQUIRE + PLAN** 应在 **30%** 内完成
- **EXECUTE** 核心��务应在 **50%** 前完成
- **REVIEW** 和收尾工作使用剩余空间
- 如果 PLAN 就用了 40%+，说明计划太复杂，应拆分为多个子计划

## 上下文紧张时的策略

1. **优先保存**：检查点 > 执行新任务
2. **压缩输出**：减少解释，增加结构化数据
3. **委托子任务**：使用 Agent 工具分担上下文压力
4. **及时分会话**：大型任务拆成多个会话，通过五文件传递状态（五文件位于 workspace，路径由 `$STARK_SESSION_DIR` 决定，详见 `shared-rules/session-workspace.md`）

## Step 0: 启动信息收集（RESEARCH 最先执行）

> **核心原则**：planner 主动问，用户只需回答。不要求用户记住任何提示词格式。

进入 RESEARCH 后，**先检查用户的初始 prompt 是否已包含足够信息**。如果以下关键信息缺失，主动发起启动询问：

### 判断逻辑

```
用户 prompt 已包含：需求描述 + 设计文档路径/内容 + 验收标准？
├── 全有 → 跳过询问，直接进入路径判断
├── 部分有 → 只问缺失项
└── 只说了一句话（如 "/cc-planner 优化性能"）→ 完整询问
```

### 启动询问模板

```markdown
收到，开始规划前需要确认几个信息：

**1. 是否有现成的设计文档/技术方案？**
   - 有 → 请提供路径或直接贴内容（vault / wiki / 本地路径 / 粘贴均可）
   - 没有 → 我来分析代码后出方案

**2. 验收标准**：怎样算做完？
   - 例：编译通过、单测通过、接口响应 < 500ms、某某功能可用...

**3. 约束**（可选）：有什么不能改的？
   - 例：不改公共接口签名、不引入新依赖、只改某某模块...

> 不确定的直接跳过，我来判断。
```

### 根据回答自动路由

| 用户回答 | 路由 |
|---------|------|
| 提供了设计文档路径/内容 | **设计文档驱动 RESEARCH**（快速通道） |
| 说"没有设计"或未提及 | **标准 RESEARCH**（从零探索） |
| 说"帮我设计" | 标准 RESEARCH → PLAN 含 DESIGN 子阶段 |

收集完成后，将信息写入 `{workspace}/session.yaml` 的 `startup_context` 字段，供后续阶段使用。

## 设计文档驱动 RESEARCH

> **适用场景**：设计文档已在 vault/wiki 完成，Claude 接手进行开发实现。
> **核心转变**：RESEARCH 从"从零探索"变为"消化设计 → 验证可行性 → 生成改动计划"。
> **与 PLAN 阶段 DESIGN 子阶段的关系**：设计文档已存在时，PLAN 阶段的 DESIGN + DESIGN-REVIEW 子阶段自动跳过（设计验证已在此完成）。

### Step 1: Agent 审视理解

派发 cc-researcher subagent，消化设计文档 + 分析当前代码现状：

```
🤖 cc-researcher ← planner.RESEARCH | 任务: 设计文档审视理解
```

````
Agent(
  subagent_type="cc-researcher",
  max_turns=8,
  description="审视理解: 设计文档消化",
  prompt="你是设计文档消化专家。

    **设计文档路径**: {design_doc_path}
    **项目根目录**: {project_root}

    **任务**：
    1. 读取设计文档，提取：
       - 功能目标（What）
       - 架构决策（How）
       - 变更范围（Where）— 新增/修改的文件和类
       - 约束条件（Constraints）
       - 接口/数据模型定义

    2. 探索当前代码库，验证设计假设：
       - 设计中引用的类/接口是否存在？签名是否匹配？
       - 设计中复用的模式在代码中是否一致？
       - 是否有设计文档未提及的隐式依赖？

    3. 产出结构化理解报告：

       ## 设计理解
       ### 功能要点
       - [要点]: [说明]

       ### 架构决策
       | # | 决策 | 理由 | 代码验证状态 |
       |---|------|------|------------|

       ### 变更范围
       #### 新增
       | 文件路径 | 类型 | 说明 |
       |---------|------|------|

       #### 修改
       | 文件路径 | 变更点 | 当前代码状态 |
       |---------|--------|------------|

       ## 代码现状
       ### 可复用组件
       | 组件 | 位置 | 设计中用途 |
       |------|------|-----------|

       ### 现有模式
       | 模式 | 位置 | 与设计一致？ |
       |------|------|------------|

       ## Gap 分析
       | # | 设计假设 | 代码现实 | 差异说明 |
       |---|---------|---------|---------|

       ## 风险与注意事项
       - [风险]: [说明]

    **强制约束**：
    1. 只读模式，禁止修改任何文件
    2. 引用的类名、方法名必须来自 Read 工具确认
    3. 输出不超过 200 行
    4. 未找到的代码实体标记为 ❌ 待创建"
)
````

### Step 2: Agent 对抗确认

从 Step 1 的理解报告中提取结论清单（仅结果，不含推理链），派发对抗验证 agent。

> 复用 `shared-rules/adversarial-verification.md` 协议。场景 = 设计理解验证。

````
Agent(
  subagent_type="cc-researcher",
  max_turns=6,
  description="对抗验证: 设计理解确认",
  prompt="你是混合对抗验证研究员。

    设计文档路径: {design_doc_path}
    项目根目录: {project_root}

    初始理解结论（仅结果，不含推理链）：
    {understanding_conclusions_list}

    **Phase A — 定向对抗**（60% 精力）：
    逐条审视，对每条问'这个理解在什么条件下是错的？'：
    - 设计说复用某组件 → 验证该组件能否被复用（签名、依赖、访问权限）
    - 设计假设某接口存在 → 验证接口签名是否匹配
    - 设计的变更范围 → 验证是否遗漏了受影响的文件
    找到反例→记录反驳+证据；找不到→记录确认+检查说明。

    **收尾覆盖补充**（40% 精力）：
    放下初始结论，独立扫描设计文档和代码，找初始理解未提到的：
    - 遗漏的依赖关系
    - 未考虑的边界条件
    - 设计文档自身的矛盾或模糊点

    输出格式：
    ## Phase A: 定向对抗
    | # | 初始结论 | 判定 | 证据 |
    |---|---------|------|------|

    ## 收尾覆盖补充
    - [新发现/无额外发现]

    ## 覆盖报告
    - 检查维度: [已检查维度]
    - 读取文件: [已读文件]
    - 未覆盖区域: [如有]"
)
````

可观测性日志：
```
🔍 对抗验证: 设计理解 | 输入: {design_doc_path} | 初始结论: {N}条
🔍 验证完成: 确认 {N} | 反驳 {N} | 盲区 {N} | 未覆盖 {N} | 质量: [充分/不充分]
```

验证质量检查：Phase A 覆盖率 ≥70%、有收尾覆盖补充段落、文件读取 ≥2、有覆盖报告。不满足 → 重派 1 次。

Lead 综合对比（防偏规则见 adversarial-verification.md §5）后更新 `{workspace}/findings.md`。

### Step 3: 生成改动设计文档

基于 Step 1 审视理解 + Step 2 对抗验证，Lead 生成**改动设计文档**。

> 模板见 `templates/templates-change-design.md`

**核心内容**：
1. **源设计文档引用**（路径 + 一句话目标）
2. **设计理解摘要**（对抗验证后的确认版本）
3. **变更范围**（新增/修改/不应触及，含文件路径）
4. **Gap 分析**（设计假设 vs 代码现实，含对抗验证发现）
5. **实现注意事项**（来自对抗验证的风险和盲区发现）
6. **验证策略**（验收标准 + 验证方式）

### Step 4: 写入 Obsidian Vault + 更新 session.yaml

改动设计文档写入路径规则：
- 源设计文档在 `vault/{项目名}/需求/` 下 → 同目录：`{功能名称}_改动设计.md`
- 源设计文档在 `vault/{项目名}/切片需求/` 下 → 同目录：`{功能名称}_改动设计.md`
- 其他 → `vault/{项目名}/需求/{功能名称}_改动设计.md`

```
📝 改动设计文档: {vault_path}
```

写入后：
1. 检查 `首页.md` 的 `search_index` 是否需要更新
2. **⛔ 强制更新 `{workspace}/session.yaml`**：
   ```yaml
   research_path: "design-doc-driven"
   design_doc_path: "{改动设计文档的 vault 路径}"
   design_review_status: "skipped"  # 设计验证已在 RESEARCH 对抗确认中完成
   ```
   > 此更新是 PLAN 阶段跳过 DESIGN 子阶段和 EXECUTE 前置检查的前提条件。未更新 → PLAN 误触发 DESIGN → 重复设计。

### 阶段完成标准（设计文档驱动路径）

- [ ] 设计文档已被 Agent 审视理解
- [ ] 理解结论已经对抗验证
- [ ] `{workspace}/findings.md` 已创建（含设计理解 + 对抗验证综合结果）
- [ ] 改动设计文档已写入 Obsidian vault
- [ ] Gap 分析已完成（设计假设 vs 代码现实）

**下一阶段判断**：
- 对抗验证发现 P0 分歧（需要用户确认） → INQUIRE
- 其他 → 直接进入 PLAN（PLAN 阶段跳过 DESIGN 子阶段）

## 标准 RESEARCH 工作流程

> 适用场景：无设计文档，从需求原始态出发探索

### Step 1: 理解需求

```markdown
## 需求理解

### 功能目标
- [ ] 主要功能是什么？
- [ ] 解决什么问题？
- [ ] 谁是使用者？

### 输入输出
- [ ] 输入数据来源和格式？
- [ ] 输出结果格式和去向？

### 边界条件
- [ ] 最大/最小值？
- [ ] 空值处理？
- [ ] 异常情况？
```

### Step 2: 探索代码结构

```yaml
Java 后端项目探索顺序:
  1. 项目根目录结构
  2. 相关的 Controller
  3. 对应的 Service
  4. Repository / Mapper
  5. 实体类 / DTO
  6. 配置文件
```

### Step 3: 分析现有模式

```markdown
## 现有模式分析

### 设计模式
- [ ] Controller 结构（RESTful 风格？）
- [ ] Service 分层（单一职责？）
- [ ] 事务管理方式
- [ ] 异常处理模式

### 代码风格
- [ ] 命名规范、注释风格、日志规范、返回值封装

### 数据访问
- [ ] 查询方式（Condition API？原生 SQL？）
- [ ] 批量处理方式、分页方式
```

### Step 4: 识别约束条件

```markdown
## 约束条件

### 技术约束
- 框架版本：Spring Boot x.x | 数据库：MySQL x.x | 中间件：Redis / MQ

### 业务约束
- 数据权限 | 操作权限 | 审计要求

### 性能要求
- 响应时间 | 并发量 | 数据量
```

### Step 5: 识别模糊点

```yaml
模糊点检测:
  边界未定义:
    - [ ] 最大/最小值、空值/异常处理、并发/性能要求
  多种实现方式:
    - [ ] 多个可选方案、同步 vs 异步、简单 vs 复杂
  缺失约束:
    - [ ] 数据格式、错误处理策略、权限要求
  隐式假设:
    - [ ] 假设了某种技术栈/业务规则？
```

输出到 `{workspace}/findings.md` "待澄清问题"章节，按高/中/低优先级分类（workspace 路径由 `$STARK_SESSION_DIR` 决定）。

### Step 5.1: 研究阶梯补充（S1→S2→S3）

> 引用 `inquiry-protocol.md` §2 自主研究协议

Step 5 识别到"多种实现方式"时，在送入 INQUIRE 前先走研究阶梯自主解决：

- **S1 代码库**（Step 2/3 已覆盖）：确认现有代码是否已有先例
- **S2 知识库**：obsidian search 查业务域历史决策、设计背景
- **S3 网络**：符合 §2 触发条件时（架构选型、性能优化、最佳实践演进等），WebSearch 查业界最佳实践

研究结果按下方"外部调研存储规则"格式写入 `{workspace}/findings.md`。研究后仍有模糊点的才进入 INQUIRE。

### 外部调研存储规则

当任务涉及 WebSearch/WebFetch 时，**必须**存储到 `{workspace}/findings.md`：

```markdown
## findings.md 必填内容

### 来源信息
- URL 链接、调研时间

### 关键发现
- 核心结论、可操作建议

### 决策依据
- 选择的方案、原因、被否决的方案及原因

### 约束条件
- 技术限制、兼容性要求
```

## 工作流程

### Step 1: 理解确认（TAC 模式：Tell → Ask → Conditional）

```markdown
## 我的理解

基于 RESEARCH 阶段的分析，我理解您需要：

### 功能目标
- [功能 1]: [说明]

### 预期输入输出
- 输入: [描述] / 输出: [描述]

### 边界条件
- [边界 1]: [处理方式]

---
**请确认以上理解是否正确？如有偏差请指出。**
```

### Step 2: 模糊点识别

自动检测需求中的模糊点：边界未定义 | 业务逻辑不明确 | 缺失业务约束 | 隐式业务假设

### Step 3: 分类提问（四层澄清框架）

```
L1: 需求澄清（What）→ 功能范围、用户场景、边界条件
L2: 约束确认（Constraints）→ 性能、业务约束（技术栈已在 Skills 中固定）
L3: 设计选择（How）→ 业务处理方式选择（附方案对比）
L4: 决策确认（Decision）→ 最终确认，准备进入 PLAN
```

**问题数量控制**：单次最多 4-6 个核心问题

| 优先级 | 数量上限 | 处理方式 |
|--------|---------|---------|
| 高（必须澄清） | 2-3 个 | 本次必须解决 |
| 中（建议澄清） | 2 个 | 尽量本次解决 |
| 低（可选澄清） | 1 个 | 可带入 PLAN |

### Step 3.5: AskUserQuestion 最佳实践速查

| 维度 | 要求 |
|------|------|
| **何时用** | 需要用户在 2-4 个互斥选项中做决策时；不适用于开放讨论、已有详细规范、或仅需 1-2 个简单确认 |
| **问题设计** | 清晰、具体、单维度；header 最多 12 字符；每个选项附描述；选项不互斥时启用 `multiSelect` |
| **批次控制** | 单批最多 4 题；复杂项目可分批（范围→架构→优先级→集成）；数禾技术栈已固定，架构类通常跳过 |
| **示例** | `question: "订单状态如何处理？"` / `header: "状态更新"` / `options: [{label: "同步更新", description: "实时，可能阻塞"}, {label: "异步队列", description: "MQ 处理，有延迟"}]` |

### Step 4: 记录并确认

将用户回答记录到 `{workspace}/findings.md` "用户确认记录"章节：

```markdown
## 用户确认记录

### 确认时间: {{timestamp}}

### 需求确认
| 问题 | 用户回答 |
|------|---------|

### 设计决策
| 决策点 | 用户选择 | 原因 |
|--------|---------|------|
```

## 主动承认不确定

**推荐**："我不确定 X 是否需要 Y，请确认" | "关于 Z 我有两种理解，请帮我选择"

**禁止**：假装理解然后猜测 | 跳过不确定的部分 | 用模糊语言掩盖不确定性

> 完整认知卫生规则见 `inquiry-protocol.md` §4
