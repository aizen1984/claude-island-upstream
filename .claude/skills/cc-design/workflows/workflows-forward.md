# 设计文档生成工作流（/cc-design）

## 目标

根据需求描述生成技术设计文档，为后续开发提供清晰指导。

**核心原则**：复杂度感知，按需设计，任务跟踪

> ⚠️ 所有文档输出必须遵循 [../templates.md](../templates.md) 中的「文档表达原则」：一句话先行、结构可视化、表格优于段落、粗体做路标。文档信息之后必须包含「快速熟悉」章节。

---

> 强制任务跟踪规则详见 SKILL.md "强制任务跟踪" 章节

---

## 工作流程总览

```
Phase 1: 复杂度分析 → Phase 2: PRD 生成（大型） → Phase 3: 技术设计 → Phase 3.5: 图表生成 → Phase 4: 设计审查 → Phase 5: 输出验证
```

---

## Phase 1: 复杂度分析

### 评估维度

```yaml
文件数量:    小型: 1-2 | 中型: 3-5 | 大型: 6+
模块跨度:    小型: 单模块 | 中型: 2-3 模块 | 大型: 跨多模块
依赖复杂度:  小型: 无新依赖 | 中型: 1-2 新依赖 | 大型: 多个新依赖/外部系统
```

> **阈值 rationale**（为什么是 1-2 / 3-5 / 6+）：
> - **小型 1-2 文件**：单次 PR 认知成本 < 10 分钟（约等于一次 code review 心流窗口），可由 code-writer 直接 TDD 实现，无需先写 PRD
> - **中型 3-5 文件**：单次 PR 认知成本 10-30 分钟，涉及跨类协作，需要技术设计但可跳过独立 PRD（业务目标已由 planner 上游传递）
> - **大型 6+ 文件**：突破单 PR cognitive budget 上限（参考 Google Engineering Practices "small CLs" 建议 ≤ 200 行 / ≤ 7 文件），必须先 PRD 对齐业务，再拆技术设计，再经独立审查
> - 临界值"6"来源：单人 1-2 小时 code review 可覆盖的最大文件数（大多数团队经验值）

### 决策矩阵

| 复杂度 | PRD | 设计文档 | 直接实现 |
|--------|-----|---------|---------|
| 大型 | 需要 | 需要 | 不可 |
| 中型 | 不需要 | 需要 | 不可 |
| 小型 | 不需要 | 不需要 | 可以 |

### 输出模板

```markdown
## 复杂度分析

| 维度 | 评估 | 说明 |
|------|------|------|
| 文件数量 | [大/中/小] | 预计 N 个文件 |
| 模块跨度 | [大/中/小] | 涉及 [模块列表] |
| 依赖复杂度 | [大/中/小] | [依赖说明] |

**复杂度**: [大型/中型/小型]
**处理策略**: [PRD → 设计文档 / 设计文档 / 直接实现]
```

### 小型任务退出路径

当 Phase 1 判断为**小型**时：

1. 告知用户：该需求复杂度较低，不需要设计文档
2. 将剩余 Phase 的 Task 标记为 `completed`（跳过）
3. 建议用户直接使用 `cc-planner` 进行任务规划或 `cc-code-writer` 直接实现

```markdown
该需求复杂度为**小型**（预计 1-2 个文件、单模块），无需设计文档。

建议下一步：
1. 使用 cc-planner 进行任务规划（推荐）
2. 使用 cc-code-writer 直接实现
```

## Phase 2: PRD 生成（大型任务）

中型/小型任务跳过此 Phase，直接标记为 completed。

### PRD 结构

PRD 包含以下核心章节：背景与问题描述、功能目标与边界、用户故事与验收标准、非功能需求（性能/安全）。

详细 PRD 模板见 [../templates.md](../templates.md) PRD 模板章节。

## Phase 3: 技术设计

### 现状代码质量扫描（重构/改造场景必执行）

> 当 Phase 1 识别为重构/改造/升级场景时，在技术设计前先扫描现有代码质量问题，作为设计输入。

**扫描维度**（引用 `cc-java-backend` 核心红线）：

| 扫描项 | 检查方法 | 对应红线 |
|--------|---------|---------|
| 事务完整性 | 搜索多表写入方法是否有 `@Transactional(rollbackFor)` | 红线 #2 |
| 类型安全 | Controller 返回值是否使用 `Result<DTO>` 而非 `Map` | 补充规则 |
| 性能模式 | 是否存在循环查库（N+1） | 红线 #1 |
| 精度问题 | 金额计算是否使用 `BigDecimal` 而非 `double` | 红线 #9 |
| 编码规范 | 字符串比较是否使用 `equals()` 而非 `==` | 红线 #8 |
| SQL 安全 | MyBatis 参数是否使用 `#{}` 而非 `${}` | 补充规则 |

**输出**：将发现的问题整合到重构方案的"现状问题"章节，每个问题附代码路径引用。

### 设计要点

#### 架构设计

整体分层（Controller -> Service -> Repository）、模块划分（职责与关键类）、依赖关系。

#### 接口定义

每个 API 需明确：请求方法/路径、请求参数（字段/类型/必填/描述）、响应结果、错误码。

#### 数据模型

每张表需明确：字段定义（类型/约束/说明）、索引设计。

#### 事务边界

事务划分（操作/范围/隔离级别）、分布式事务方案（场景/方案/说明）。

详细模板见 [../templates.md](../templates.md) 技术设计文档模板章节。

### 与 cc-api-analyzer 条件集成

> 当设计涉及现有系统接口复用时，自动委托 cc-api-analyzer 获取接口清单和调用链。

**触发条件**（满足任一即触发）：
- 需求涉及对现有 API 的修改或扩展
- 需要分析现有接口的调用链以评估影响范围
- 跨模块接口调用需要确认兼容性

**委托流程**：
1. 使用 cc-api-analyzer 分析指定 Controller → 获取 API 清单和调用链
2. 基于分析结果完善接口定义（复用/扩展决策）
3. 将 cc-api-analyzer 产出整合到技术设计文档的接口定义章节

**委托失败恢复**：cc-api-analyzer 超时或失败 → 降级为手动接口文档编写，标记为"待补充"

### Phase 3 变体：重构方案设计

> 当 Phase 1 识别为"重构"场景（用户输入含"重构""迁移""架构升级"）时，Phase 3 替换为此变体流程。

**与标准 Phase 3 的差异**：

| 维度 | 标准（新功能） | 重构变体 |
|------|--------------|---------|
| 输入 | 需求描述 | 现有代码 + 重构目标 |
| 核心分析 | 接口定义 + 数据模型 | 现状分析 + 目标状态 + 迁移路径 |
| 必含章节 | 架构设计、接口定义、数据模型 | 现状问题、目标架构、迁移策略、向后兼容 |
| 风险维度 | 技术风险 | 技术风险 + **回归风险** + **数据迁移风险** |

**重构触发判断**：用户输入含以下关键词时进入重构变体——"重构""迁移""架构升级""拆分""解耦""替换"。"优化"需结合上下文：若指架构层面优化（如"优化订单系统架构"）→重构变体；若指代码级优化（如"优化这个方法性能"）→标准流程。

**重构方案必含章节**：

1. **现状问题**：当前架构/代码的具体问题点（附代码路径引用）。建议扫描维度：事务完整性、类型安全（Map vs DTO）、性能模式（N+1）、精度问题（double vs BigDecimal）、编码规范（== vs equals）
2. **目标架构**：重构后的目标状态（含架构图）
3. **迁移策略**：分阶段迁移计划，每阶段可独立验证
4. **向后兼容**：过渡期新旧共存方案（如有）
5. **重构可行性评估**：影响面分析（涉及文件数、调用方数量、测试覆盖率）
6. **回滚方案**：每个迁移阶段的回滚步骤

**审查清单扩展**（Phase 4 追加检查项）：
- [ ] 迁移策略是否可分阶段执行（禁止 big-bang 重构）
- [ ] 每个阶段是否有独立验证方式
- [ ] 向后兼容方案是否可行
- [ ] 回滚方案是否可操作

## Phase 3.5: 图表生成（委托 cc-diagram）

> Phase 3 技术设计完成后，自动委托 cc-diagram 生成 Mermaid 图表，嵌入到设计文档中。

### 触发条件

Phase 3 完成后**自动触发**，无需用户显式请求。

### 图表生成规则

根据设计内容按需生成以下图表（至少生成 1 个，按需组合）：

| 图表类型 | 触发条件 | 嵌入位置 |
|---------|---------|---------|
| **类图**（classDiagram） | 涉及 2+ 核心类/接口/继承关系 | 架构设计章节（2.2，整体架构图之后） |
| **序列图**（sequenceDiagram） | 涉及跨模块/跨系统交互流程 | 业务逻辑设计章节（5.x） |
| **ER 图**（erDiagram） | 涉及 2+ 数据表且有关联关系 | 数据设计章节**末尾**（4.x 最后） |
| **状态图**（stateDiagram-v2） | 涉及状态机/生命周期流转 | 业务逻辑设计章节（5.x） |
| **流程图**（flowchart） | 涉及复杂决策分支/多步骤流程 | 业务逻辑设计章节（5.x） |

### 嵌入位置原则：先总后分

> **强制规则**：读者必须先通过「变更全景」知道"改了什么"，再看图表细节。图表是"可视化验证"而非"首次信息输入"。

```
阅读链条（正确顺序）：
  快速熟悉.变更全景（🟢新增/🔵变更/🔴删除/🟣核心/🟠外部/⚪不变）
      ↓
  快速熟悉.核心架构（调用链树形图）         ← 带着变更认知看全局串联
      ↓
  架构设计.整体架构（分层图）               ← 展开层次结构
      ↓
  架构设计.类图（Mermaid，颜色对应变更全景） ← 可视化验证类间关系
      ↓
  模块划分 → 依赖关系 → 技术选型           ← 展开细节
```

### 委托数据格式

按 `shared-rules/data-contracts.md` 传递：

```yaml
diagram_type: "classDiagram"  # 或 sequenceDiagram/erDiagram/stateDiagram-v2/flowchart
diagram_data: |
  # Phase 3 中提取的结构化数据：
  # - 类图：类名、属性、方法、继承/实现/依赖关系
  # - ER 图：表名、字段、表间关系
  # - 序列图：参与者、调用顺序、返回值
  # - 状态图：状态列表、转换条件
title: "功能名称 - 图表标题"  # 可选
highlights:  # 视觉重点标注（强制）
  newAdd: ["新增类/节点名"]    # 🟢 绿色 — 新增
  modified: ["变更类/节点名"]  # 🔵 蓝色 — 变更
  core: ["核心类/节点名"]      # 🟣 紫色 — 核心/扩展点
  external: ["外部系统名"]     # 🟠 橙色 — 外部系统
```

### 输出要求

1. 生成的 Mermaid 代码块直接嵌入设计文档对应章节（非单独文件）
2. 每个图表前加一句话说明图表展示的内容
3. 每个图表后加图例表格（仅列实际使用的样式）
4. 图表遵循 cc-diagram 的八条防错规则
5. **图表必须遵循 cc-diagram 的「视觉重点规范」**：
   - 🟢 新增用 `:::newAdd`（绿色）
   - 🔵 变更用 `:::modified`（蓝色）
   - 🔴 删除用 `:::deleted`（红色）
   - 🟣 核心/扩展点用 `:::core`（紫色）
   - 🟠 外部系统用 `:::external`（橙色）
   - 已有元素用默认样式
6. **图表必须包含辅助理解的备注**（至少 1 条）：设计决策、关键约束、交互说明或业务规则。备注语法见 cc-diagram 备注规范。

### 降级处理

| 场景 | 处理方式 |
|------|---------|
| cc-diagram 未加载 | 使用 ASCII 树形图/箭头链替代（保持当前行为） |
| 图表渲染失败 | 保留 ASCII 版本，标记"待补图" |
| 小型任务（Phase 1 退出） | 跳过此阶段 |

## Phase 4: 设计审查

### 审查清单

```markdown
### 完整性检查
- [ ] 所有接口已定义
- [ ] 所有实体已设计
- [ ] 异常场景已覆盖
- [ ] 边界条件已处理
- [ ] 风险与缓解章节：至少 3 个风险，含降级策略
- [ ] 验证方案章节：异步链路/外部对接有明确验证方式
- [ ] 已确认/待确认章节：待确认项有影响范围和当前假设
- [ ] 参数映射表：涉及外部对接的接口有字段来源/去向

### 一致性检查
- [ ] 命名规范一致
- [ ] 接口风格一致
- [ ] 错误处理一致

### 表达规范检查
- [ ] 快速熟悉与正文图表互补不冗余
- [ ] 代码块 ≤ 30 行，无完整实现
- [ ] 文档 > 300 行时有目录导航
- [ ] 设计决策有对比论证表

### 风险识别
| 风险 | 可能性 | 影响 | 缓解措施 |
|------|--------|------|---------|

### 审查结论
- [ ] 设计完整，可以进入开发
- [ ] 需要补充：[待补充项]
- [ ] 需要重新设计：[原因]
```

### 审查执行者

| 场景 | 审查执行者 | 说明 |
|------|-----------|------|
| design 被 planner 委托触发 | planner 控制流 + 用户门控 | 设计文档返回 planner，由 planner 展示评审提示，用户决策 |
| 用户直接触发 design | 设计审查 + 用户确认 | design 自身执行审查清单，输出结果供用户确认 |

### 通过标准

| 维度 | 通过条件 |
|------|---------|
| 完整性 | 所有接口已定义 + 所有实体已设计 + 异常场景已覆盖 + 风险/验证/确认章节齐全 |
| 一致性 | 命名规范统一 + 接口风格统一 + 错误处理统一 |
| 表达规范 | 互补不冗余 + 代码块 ≤ 30 行 + 长文档有目录 + 决策有对比表 |
| 可行性 | 无明显技术风险 或 风险已有缓解措施 |

### 失败处理流程

| 审查结果 | 处理方式 |
|---------|---------|
| 完整性缺失 | 返回 Phase 3 补充缺失内容 |
| 一致性问题 | 就地修正（不回退 Phase） |
| 重大风险 | 标记风险 + 询问用户是否继续 |
| 用户要求修改 | 记录修改意见，返回 Phase 3 重新设计（最多 3 次循环） |
| 3 次修改仍不通过 | 强制暂停，提供选项：(A) 继续修改 (B) 简化设计 (C) 终止流程 |

## 输出示例

```markdown
# 用户积分系统 技术设计文档

## 快速熟悉（3 分钟读完）

### 一句话概括

用户积分系统通过 **规则引擎**（PointRuleService）+ **账户模型**（PointAccount）统一管理积分的生命周期：**规则配置 → 积分发放 → 消费兑换 → 过期回收**。

### 核心架构

```
触发源（订单完成/签到/活动）
    ↓
PointController（HTTP 入口）
    ↓
PointService（业务调度）
├── PointRuleService    ← 规则匹配：该发多少分
├── PointAccountService ← 账户操作：加减余额
├── PointRecordService  ← 流水记录：每笔变动
└── PointExchangeService ← 兑换逻辑：积分换券
        ↓
    ┌──────────────────────────────┐
    │ 数据层                       │
    │ point_account  — 账户余额    │
    │ point_record   — 变动流水    │
    │ point_rule     — 规��配置    │
    │ point_exchange — 兑换记录    │
    └──────────────────────────────┘
```

### 全景速览

| 维度 | 概要 |
|------|------|
| 涉及模块 | **积分**、订单、用户 3 个模块 |
| 新增接口 | **6 个**（增减查兑换+规则管理） |
| 新增表 | **4 张**（account/record/rule/exchange） |
| 外部依赖 | Redis（缓存余额）、OrderService（订单回调） |

### 关键设计决策

1. **账户模型而非流水汇总**：余额实时更新到 account 表，避免每次汇总 record 表
2. **规则引擎独立**：积分规则与发放逻辑解耦，支持运营自助配置

---

## 1. 复杂度分析

| 维度 | 评估 | 说明 |
|------|------|------|
| 文件数量 | 大型 | 预计 12 个文件 |
| 模块跨度 | 大型 | 积分、订单、用户 3 个模块 |
| 依赖复杂度 | 中型 | 需要 Redis 缓存 |

**综合判断**: 大型任务，需要 PRD + 设计文档

## 2. 架构设计

| 模块 | 职责 | 核心类 |
|------|------|--------|
| point-account | **积分账户**：余额增减、冻结解冻 | PointAccountService |
| point-record | **变动流水**：每笔操作记录 | PointRecordService |
| point-rule | **规则引擎**：发放规则匹配 | PointRuleService |
| point-exchange | **积分兑换**：积分换券/商品 | PointExchangeService |

## 3. 接口定义

> **一句话**：6 个接口覆盖积分 CRUD + 兑换 + 规则管理

### POST /api/points/add — 增加积分

**请求**:
```json
{
  "userId": "long, 必填, 用户ID",
  "points": "int, 必填, 积分数量",
  "reason": "string, 必填, 变动原因"
}
```

**响应**:
```json
{
  "code": 200,
  "data": { "balance": 1000, "recordId": 12345 }
}
```

## 4. 数据模型

> **一句话**：4 张表，account 存余额、record 存流水、rule 存规则、exchange 存兑换

### point_account 表 — 积分账户

| 字段 | 类型 | 说明 |
|------|------|------|
| id | bigint | 主键 |
| user_id | bigint | 用户ID |
| balance | int | **当前余额** |
| total_earned | int | 累计获得 |
| total_spent | int | 累计消费 |

## 5. 事务边界

| 操作 | 事务范围 | 原因 |
|------|---------|------|
| 增加积分 | account + record | **余额和流水必须一致** |
| 扣减积分 | account + record + 业务表 | 涉及兑换场景 |
