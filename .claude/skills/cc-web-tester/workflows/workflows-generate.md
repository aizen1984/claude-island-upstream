# Phase 2: GENERATE（测试用例生成）

**执行者**：主 agent

## 2.1 输入

读取 Phase 1 产出的 `功能分析报告.md`。

## 2.2 用例设计策略

采用**模式驱动 + 人工补充**的两步法，对照 [references/operation-patterns-modes.md](../references/operation-patterns-modes.md)。

### Step 1: 模式匹配与套件展开

遍历功能分析报告中每个页面标注的操作模式，自动展开标准用例套件：

```
1. 读取页面的「操作模式」字段（Phase 1 已标注）
2. 对每个模式，从 operation-patterns-modes.md 查找标准套件
3. 填充具体业务数据（实体名、字段名、按钮名、验证值）
   - 边界值用例（C5 等）：具体长度值从功能分析报告的字段校验规则提取（如报告标注 maxlength=50 则测试 51 字符），禁止使用固定魔数
   - 搜索用例（R2 等）：关键词必须从 Phase 1 探索时实际观察到的列表数据中提取（如看到记录名含"XXX"则用"XXX"作搜索词），禁止使用泛化词（如"测试"、"test"）避免环境依赖
4. 标注数据生命周期（creates/depends/consumes）
```

### Step 2: 去重与补充

```
1. 合并跨页面的重复模式（如多处搜索只需验证一处即可代表）
2. 补充模板未覆盖的业务特有用例（跨页面联动、特殊业务规则等）
3. 按页面/功能模块分组
```

### 通用维度（模板未覆盖时的兜底）

| 维度 | 说明 | 优先级 |
|------|------|--------|
| Happy Path | 标准正常操作流程 | P0/P1 |
| 必填校验 | 缺失必填字段提交 | P1 |
| 边界值 | 空值、最大长度、特殊字符 | P2 |
| 格式校验 | 邮箱、手机号、数字等格式错误 | P2 |
| 状态流转 | 多步操作的前后依赖、状态变化 | P1 |
| 权限/异常 | 越权操作、并发冲突 | P3 |

## 2.3 用例分类

| 类型 | 说明 | 执行策略 |
|------|------|---------|
| P0-冒烟 | 核心流程能跑通（如登录→列表→新增→查看） | 必测，最先执行 |
| P1-功能 | 每个功能点的正常流程 | 必测 |
| P2-边界 | 边界值、异常输入 | 建议测（可通过 priority_filter 控制） |
| P3-兼容 | 不同状态下的表现 | 可选 |

## 2.4 用例编号规则

```
TC-{三位序号}: {简要描述}
示例: TC-001: 正常新增记录
     TC-015: 编辑时清空必填字段
```

## 2.5 强制字段要求

生成的测试用例 JSON 必须遵循以下字段约束，缺失任一必须字段则视为产出不合格：

| 层级 | 字段 | 类型 | 要求 |
|------|------|------|------|
| module | `patterns` | 数组 | 必须列出该模块涉及的所有操作模式，如 `["Read", "Create", "Delete"]` |
| case | `pattern` | 字符串 | 必须标注该用例对应的操作模式，如 `"Create"`，必须来源于 operation-patterns-modes.md 的 15 种模式 |
| case | `data_lifecycle` | 对象 | 必须包含 `creates`/`depends`/`consumes` 三个子字段（无关联时填 `null`） |

**汇总统计约束**：P0/P1/P2 数量必须从生成的 JSON 中程序化计算（遍历 cases 数组统计 priority 字段），禁止手动估算或凭印象填写。

## 2.6 产出自检（Self-Verification Gate）

写入产出文件前，**必须逐项自检**（不可跳过，不可仅凭"感觉正确"）：

| 检查项 | 要求 | 校验方法 |
|--------|------|---------|
| patterns 完整性 | module.patterns 必须覆盖功能分析报告中该页面标注的**所有**操作模式 | 逐页面对比分析报告的操作模式字段 |
| 统计一致性 | md 中 P0/P1/P2/P3 数量 = JSON 中程序化计算的数量 | 遍历 JSON cases 统计 priority，与 md 统计行逐项比对 |
| 数据标注完整 | 每个 Create(C1) 用例必须有 creates；对应 Delete(D1) 必须有 consumes | 检查所有 pattern=Create 的用例 |
| 安全命名 | 测试数据名（creates 值、步骤中的输入文本）仅含字母/数字/横线/下划线/中文 | 排除 `[](){}<>!@#$%^&*` 等特殊字符 |
| 闭环完整 | 每个 creates 都有对应的 consumes（闭环型），或标记为显式清理型 | 检查 creates→consumes 对应关系 |
| 前置-步骤一致 | 前置条件描述的起始状态 = 步骤第一步的起始状态（不可矛盾） | 逐条检查：前置写"已进入X页面"则步骤不应从"点击进入X"开始 |

⚠️ **统计一致性是 Critical 检查项**：如果 md 统计与 JSON 不一致，必须修正后再输出。禁止手动估算统计数字。

## 2.7 产出

写入 `{输出目录}/测试用例/测试用例.md`，模板见 [templates.md](templates.md) 测试用例章节。

## 2.8 生成 XMind 思维导图

在写入测试用例.md 后，同步生成 .xmind 文件用于可视化评审。

```
1. 构造 JSON 中间数据（结构见 scripts/generate-xmind.py 注释）：
   - title: "{网站名称} 测试用例"
   - url: 目标 URL
   - date: 当前日期
   - modules: 按页面/功能模块分组
     - 每个 module 包含 name + patterns（操作模式数组）+ cases 数组
     - 每条 case: id, title, priority, pattern, data_lifecycle, precondition, steps, expected
2. 将 JSON 写入 {输出目录}/测试用例/测试用例.json（中间文件）
3. 执行脚本生成 xmind：
   python3 {skill目录}/scripts/generate-xmind.py {输出目录}/测试用例/测试用例.json {输出目录}/测试用例/测试用例.xmind
4. 确认文件生成成功
```

XMind 思维导图结构：
```
根节点（网站名称 测试用例）
├── 模块 A
│   ├── P0 (N)
│   │   ├── TC-001: 用例标题 [P0]
│   │   └── TC-002: ...
│   ├── P1 (N)
│   │   └── ...
│   └── P2 (N)
│       └── ...
├── 模块 B
│   └── ...
```

写入完成后 → 告知用户 xmind 为测试用例主文件，可用 XMind 打开编辑 → AskUserQuestion 等待用户确认。

**提示用户格式**：
```
测试用例已生成：
- 测试用例.xmind ← 主文件，请用 XMind 打开查看/编辑
- 测试用例.md   ← 同步文档

如需调整用例，请直接编辑 xmind 文件（增删改用例、调整优先级、修改步骤等），
编辑完成后告诉我，我会自动同步回 .md 文档。
确认无误后回复"确认"进入执行阶段。
```

# Phase 2.5: SYNC（xmind 反向同步）

**执行者**：主 agent
**触发条件**：用户确认可以进入 Phase 3 时，自动执行

## 2.5.1 检测 xmind 变更

```
1. 读取当前 测试用例/测试用例.xmind 的修改时间
2. 与 测试用例/测试用例.json 的修改时间比较
3. 如果 xmind 更新（修改时间晚于 json），执行反向同步
4. 如果 xmind 未修改，跳过同步，直接进入 Phase 3
```

## 2.5.2 反向同步流程

```
1. 执行 xmind → JSON：
   python3 {skill目录}/scripts/xmind-to-json.py {输出目录}/测试用例/测试用例.xmind {输出目录}/测试用例/测试用例.json

2. 执行 JSON → MD：
   python3 {skill目录}/scripts/json-to-md.py {输出目录}/测试用例/测试用例.json {输出目录}/测试用例/测试用例.md

3. 输出变更摘要（与同步前对比）：
   - 用例总数变化：N → M
   - 新增用例：[列出新增的 TC 编号]
   - 删除用例：[列出删除的 TC 编号]
   - 修改用例：[列出内容变化的 TC 编号]

4. AskUserQuestion 确认同步结果无误 → 进入 Phase 3
```

## 2.5.3 用户在 XMind 中可执行的操作

| 操作 | 在 XMind 中如何做 | 同步行为 |
|------|-----------------|---------|
| 新增用例 | 在优先级分组下添加子节点，标题格式 `TC-NNN: 描述` | 自动识别并同步 |
| 删除用例 | 删除用例节点 | 从 md 中移除 |
| 修改标题 | 直接编辑节点标题 | 同步更新 |
| 修改优先级 | 移动用例到不同优先级分组下 | 同步更新 |
| 修改步骤/预期 | 编辑节点备注（notes） | 同步更新 |
| 新增模块 | 在根节点下添加子节点 | 自动识别为新模块 |
| 调整顺序 | 拖拽排序 | 按新顺序同步 |
